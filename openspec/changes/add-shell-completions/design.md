# Design

## Context

See `proposal.md` for motivation. The CLI is defined with Clap derive in `src/cli.rs`; it has no completion entry point. Persisted workspace, claim, and origin IDs live in SQLite. `database::open_read_only` opens existing storage without creating a database or applying migrations. In contrast, `open_default` can create and migrate storage.

Status loading includes relationships, process observation, and optional user-controlled hooks, so it is unsuitable as a completion data source. Nix and release archives currently install only the binary and supporting notices.

## Goals / Non-Goals

**Goals:** Keep suggestions aligned with the parsed CLI and make ID lookup cheap and read-only. Cover every ID argument through one reusable module. Preserve the distinction between workspace-only and cross-entity selectors. Let each installation load completion using its installed binary.

**Non-Goals:** Validate whether a suggested workspace can currently be claimed, opened, released, or removed; complete arbitrary URLs, program arguments after `--`, or shells other than Bash and `zsh`; change normal command parsing or storage schema.

## Decisions

### 1. Use Clap's Dynamic Completion Engine

Add `clap_complete` with its `unstable-dynamic` feature. Call `CompleteEnv::with_factory(completion::command).var("TREES_COMPLETE").complete()` before normal argument parsing or any output. The factory builds `Cli::command()` and adds completion metadata, keeping the derived CLI grammar as the source of commands, options, and finite values.

The namespaced environment variable avoids treating unrelated `COMPLETE` settings as Trees requests. Static generated scripts with patched callbacks were considered, but would duplicate argument parsing and shell-specific quoting rules. This feature's protocol is unstable. Refresh registrations from the installed binary when a shell starts and test against the locked dependency version.

### 2. Query Candidate Data Directly Through Read-Only Storage

Put one shared completion module under `src/cli/`. It owns the completion command factory, ID argument binding registry, and candidate policies. Focused projections in `src/storage/` provide the read-only queries. Use a small candidate-kind enum for all workspace IDs, non-removed workspace IDs, active claim IDs, registered origin IDs, and the cross-entity union. Bind `(command, argument ID)` entries from the spec's argument table to those kinds.

Keep the binding registry in one place, including the `WorkspaceLocatorArgs` fields flattened into several commands. That shared struct cannot own a single workspace-ID callback because `status` includes removed records while other commands do not. The command factory applies the appropriate policy to each flattened instance. Register `--claim-id` even though its parse field is a `String`.

Add a coverage test that traverses the derived Clap command tree. It collects arguments whose declared value name is `ID` or ends in `_ID` and compares them with the binding registry. The current value names are `WORKSPACE_ID`, `CLAIM_ID`, `ID`, and `WORKSPACE_OR_REPO_ID`. Require future ID arguments to follow this convention, so a new argument fails the test until it has a completion binding. Keep normal parsing through `Cli::parse()` unchanged.

Open the database only when a persisted value is being completed. Storage queries select only IDs and paths needed for suggestions. Treat missing storage, schema mismatch, and query failures as empty candidate sets and emit no diagnostic during completion. Do not call status loading, Git, hooks, origin resolution, or normal command dispatch. Filter by the typed prefix, sort, and deduplicate before passing candidates to the shell adapter.

For `open` and `remove`, exclude an ID found in both workspace and origin tables from positional suggestions; an explicit `open --workspace-id` can still suggest the workspace. This only filters suggestions; each command retains its own eligibility and ambiguity checks.

### 3. Combine Registered Repository Names with Paths

For `--repo`, combine local path candidates with names derived from persisted origin source-path base names. Keep only names that identify one origin, and deduplicate overlapping path and name suggestions. Local paths retain their existing runtime precedence over names. Omit candidates with control characters that the shell protocol cannot represent safely. Do not read Git configuration or resolve remote URLs while completing. Directory-valued selectors use path completion without database access.

### 4. Load Version-Matched Shell Registrations

Document shell setup lines that source a registration generated by `TREES_COMPLETE=bash trees` or `TREES_COMPLETE=zsh trees`. Install lightweight Bash and `zsh` loader files in the Nix package's standard completion directories. Include matching files in release archives.

These loaders request a registration from `trees` when a shell starts, instead of embedding the build-time completion protocol. Verify `zsh` autoload and Bash registration with real shell processes. `cargo install` users can use the documented setup lines directly.

## Risks / Trade-Offs

- The `clap_complete` dynamic interface can change between versions. Mitigation: lock the dependency, source registrations from the running binary, and exercise both shells in tests when updating it.
- Starting a shell and requesting dynamic completion each spawn Trees. Mitigation: registration never opens storage; candidate providers use focused read-only queries and skip Git and hooks.
- A persisted candidate may become ineligible or disappear before execution. Mitigation: completion is advisory and command validation remains authoritative.
- Paths or repository names may contain shell-sensitive characters. Mitigation: use the completion engine's candidate protocol and test spaces, quotes, and control characters without interpolating names into shell source.

## Migration Plan

No migration is required. Add code, tests, documentation, and distribution files in one change. Removing the feature restores prior CLI behavior; shell startup lines and packaged loader files can then be removed independently without affecting persisted state.
